# BootBoost 缓存校验

## 问题与依据

2026-10-20 收到 Elden Ring 更新到 1.17.2 后必须删除 `cache` 才能进入游戏的反馈。仓库原有实现已经校验完整加密 BHD 的 XXH3-128、缓存格式版本、解压长度、明文校验和及 BHD 基本结构；缺少的是缓存与当前游戏 EXE、RSA 密钥的绑定，以及缓存标头与当前解密结果的直接比对。

本机安装目录中，`eldenring.exe`、`Data0.bhd`、`Data3.bhd` 的修改时间为 2026-10-20；`Data1.bhd`、`Data2.bhd`、`DLC.bhd` 的修改时间更早。仅按 BHD 内容生成缓存键时，游戏更新仍可能命中未修改 BHD 的旧缓存。

没有取得发生故障时的旧缓存和升级前的完整文件组合，因此不能将该校验缺口认定为这次启动失败的唯一原因。以下修正覆盖已确认的失效判断缺口；1.17.2 的进游戏与连续启动仍需现场验证。

## 采用的校验

| 校验对象 | 实现 | 执行时机与成本 |
| --- | --- | --- |
| 游戏 EXE | 组合内存中 PE 的 `TimeDateStamp`、`SizeOfImage`、`CheckSum`，以及文件大小、最后写入时间，生成游戏身份 | 安装资源 Hook 时查询一次文件元数据；不读取 EXE 内容 |
| 原始 BHD | 保留完整加密 BHD 的 XXH3-128 | 沿用原有读取与哈希，不增加 BHD 扫描 |
| RSA 密钥 | 对实际 PEM 字符串生成 XXH3-128，再与游戏身份、BHD 哈希组合 | 每次挂载只额外处理短 PEM 字符串和 48 字节身份数据 |
| 当前明文标头 | 比较缓存前 24 字节与本次 stub mount 已解密的标头 | 不增加 RSA 解密块或磁盘读取 |
| 缓存完整性 | 保留格式、来源键、压缩与解压长度、校验和、BHD 基本结构检查 | 沿用原有流程 |

Windows 的文件句柄信息接口可取得文件大小与最后写入时间；PE 头提供链接时间戳。这些字段用于低成本识别正常游戏更新。[GetFileInformationByHandle](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getfileinformationbyhandle)、[IMAGE_FILE_HEADER](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-image_file_header)

游戏身份排除加载地址、文件 ID、访问时间，避免 ASLR、文件位置变化或普通读取导致缓存反复失效。它不是整个 EXE 的内容哈希；保持文件大小、最后写入时间和上述 PE 字段不变的 EXE 改写不在此校验的覆盖范围内。

缓存键使用新的组合方式，旧加载器生成的缓存文件不会被命中。游戏身份、BHD 或 RSA 密钥改变后，首次挂载执行完整解密并生成新缓存；后续启动恢复缓存加速。旧文件可以保留，无需启动时遍历或清空缓存目录。当前缓存文件若损坏或与实时标头不符，则删除该文件并沿用完整挂载、重新生成流程。无法取得 EXE 身份时跳过 BootBoost，使用游戏完整挂载流程。

缓存写入仍使用临时文件、`FlushFileBuffers` 和替换操作，缓存格式版本保持 `1`；变化的是键的计算方式与加载时的实时标头检查。

## 未采用的方式

| 方式 | 原因 |
| --- | --- |
| 每次启动计算完整 EXE、BDT 哈希 | 需要扫描额外的大文件，与保留 BootBoost 启动收益的要求冲突 |
| 只校验 BHD 大小或修改时间 | 会漏掉保持这些属性不变的内容替换，因此保留完整 BHD 哈希 |
| 只读取 Steam `buildid` | 会依赖 Steam 安装目录和清单状态，无法独立覆盖手动替换游戏文件的情况 |
| 每次完整 RSA 解密后比对缓存 | 重复执行 BootBoost 要跳过的主要工作 |

文档指定的 me3 基线也采用完整 BHD 哈希及单块 stub 解密。本次保留该加速流程，增加缓存身份和实时标头检查，不改变 VFS 字典缓存优化。[me3 基线](me3-repo.md)、[基线 asset_hooks.rs](https://github.com/garyttierney/me3/blob/5f4fa47fad537b915fa9dbc01a9fb91b8a081bb5/crates/mod-host/src/asset_hooks.rs)

## 验证

Debug 全量构建、Release DLL 构建通过。Debug 的 61 项 CTest 测试通过；补充旧键隔离与无效 PE 测试后，`smoke_boot_boost` 再次通过。新增回归覆盖：

- EXE 时间戳、映像大小、PE 校验和、文件大小或最后写入时间改变时，游戏身份改变。
- 映像地址、文件访问时间改变时，游戏身份保持一致。
- RSA 密钥改变，以及 BHD 大小不变但末尾内容改变时，缓存键改变。
- 新缓存键与原来的纯 BHD 哈希键隔离；错误键被拒绝后可重新生成并加载。
- 缓存明文结构和校验和均有效，但与实时标头的标志或桶数不同，仍会被拒绝并删除。
- 原有截断、尾随数据、载荷损坏、长路径和并发写入测试保持通过。

性能对比使用修改前的 `dl_device.c/.h` 快照与修改后的生产代码，均以 MSVC Release 构建，并使用相同的 Win32 测试分配器及 miniz、xxHash。源哈希输入为本机 `Data2.bhd`，大小为 7,225,088 字节。缓存载荷是同样大小的合成 BHD，混合原文件字节与零填充；不将其视为真实游戏解密后的 BHD。

分进程基准固定到同一个可用逻辑 CPU，按旧、新、新、旧的顺序运行。每次先预热 10 次，再测 7 批、每批 100 次「完整 BHD 哈希、缓存打开和读取、解压、校验」。两版各 14 批均值的中位数为 6.709 ms、6.778 ms，变化约 1%，各批结果存在重叠。

进一步将新旧函数编入同一个进程，共享 miniz、xxHash，并固定在同一个逻辑 CPU 上交替调用，每次交换两版的先后顺序。首批用于预热，之后统计 7 批、每批每版 100 次命中。下表的命中流程结果为这 7 批均值的中位数；源键结果为前述分进程基准中每版两次各 2,000 次循环均值的平均值。

| 项目 | 修改前 | 修改后 |
| --- | --- | --- |
| 完整 BHD 缓存键计算 | 0.3268 ms | 0.3271 ms |
| 缓存命中流程，同进程交替 | 6.9676 ms | 6.9679 ms |
| EXE 元数据查询与身份计算 | 无 | 每次进程初始化约 0.032 ms |

同进程交替测量时，命中流程单批变化在 -1.15% 至 +1.58% 之间，未观察到稳定的性能退化；缓存键新增耗时约 0.3 µs。该微基准不等同于游戏启动耗时测量，不包含游戏自身的 stub mount、RSA 解密或进入菜单的时间。

本次对比源码、构建工程和原始结果保存在工作区的 `cmake-build-debug/boot-boost-baseline/`、`cmake-build-debug/boot-boost-benchmark/`；分进程固定 CPU 的结果为 `results-pinned.json`，同进程交替结果为 `results-paired.txt`。这些目录属于本地构建产物，不进入版本控制。
